# 阶段验收状态

用于阻止候选、失败版本和旧验收结论进入下游。此页为低层状态契约，不替代 [实际看图](visual-verification.md) 和 [视觉判断](quality-and-revision.md)。常规新制作直接使用[制作接口](production-api.md)生成机械字段并返回下一步；只有特殊评审/维护才读本页，不手写同义状态表。

## 阶段状态

- `unreviewed`：新结果或仍有待核对项。只能作候选/待修基线。
- `rejected`：任何关键目标失败，记录具体差异。不能作为合格设计来源。
- `approved`：当前版本所有关键目标已实际检查通过，或由有效批准加无损像素证明及制作模型构图/背景检查继承，才可作为合格图引用或交付。
- `selected_unreviewed`：达到单阶段生成上限后，制作模型自己选定最优图。允许作为下游依据和交付所选图，但保留未验收说明，不冒称合格；既有失败/待核实报告保留。

局部改善不改变整体失败状态。修改图片、参考或验收目标后，旧批准不能自动继承；重查当前哈希及受影响下游。进度文字和文件名同样区分候选/失败/合格，不用“新特写完成、同套合格”等表达掩盖尚未通过。

上述阻断规则对已记录的生成上限选优有明确例外：它不恢复视觉通过，而是允许采用未验收图继续。简单自评先于子代理，返修复用原代理，第二次起仍查看细节但合理位置/长度差异按设计接受，见 [复核流程](review-workflow.md)。

用户明确要求仅生成试跑时，记录 `unreviewed`，不执行下述验收门槛，不扩展成整套制作。用户随后认可某项效果可以记录认可范围；没有完成其他必要视觉检查，不能自动将整图改为 `approved`。以后用作合格上游或正式交付时再执行适用验收。

## 固定验收底稿

源表面有糊纹、斑块或装饰残笔时，按 [材质细节判别](surface-detail-diagnosis.md) 为材料基底和图案分别列适用的设计/质量目标，来源含有效区域、排除依据及恢复证据。观察记录内容判定与成像状态，不用一个“材质细节符合”概括。无需固定额外ID；脚本只查记录，不能自动判断斑块是否真实织纹。

根据完成的图片选用文档、特征/空间记录及实际输入用途，为各视图列检查项，包含身份、关键设计、角色本色/画风、指定光照/表情/构图、原生质量、缩小表面、背景，以及背/侧的空间关系。每项写正确来源、可观察目标；细节来源须覆盖输入图片承担的真实纹样、材料、连接与独有特征，不只登记一张主参考。按可见内容安排检查，不机械填写固定身体部位。

新制作时在调用前固定目标。评审既有图片时，在评审开始先从用户要求、有效原图及已采用方案固定目标，注明 `created_for:"existing_candidate_review"`，不伪称生成前已有底稿。未知历史提示词、输入顺序或编辑链标缺失；不补造，仍可依据可见错误拒绝候选。目标更新需有新原图事实/用户更正及影响记录，不能迁就结果或根据候选新增标准来证明它通过。

新任务的 `验收目标.json` 和 `验收状态.json` 均使用 `schema_version:2`、`rules_version:2`。规则版本与记录结构版本分别保存；示例为目标的最小片段，实际记录由助手整理：

```json
{
  "schema_version":2,"rules_version":2,
  "scope":"full_sheet","task_mode":"production",
  "sources":{"primary":{"file":"参考/主参考.png","sha256":"实际哈希"}},
  "checks":{"head":[
    {"id":"本任务身份关系","group":"identity","source_ids":["primary"],"target":"实际可观察目标"}
  ]}
}
```

这里只示范一个检查项；完整表按真实任务补足各分组：`identity`、`design`、`look`、`native_quality`、`reduced_quality`、`background`；背面和侧面另有`spatial`。完整套的四个视图均列目标。原图只在局部清楚时写其有效用途，采用背面方案另作为已记录来源，不冒充摄影事实。

`sources` 分别登记有效原始细节图/裁切、图片选用文档及指定呈现来源的真实路径与哈希；`source_ids` 指向当前检查实际需要的来源，不将另一角色的呈现图登记为身份/服装依据。默认文字呈现目标直接写入 `target`，来源可引用固定的制作文档，不要求额外示例图片。`look` 分开列本色/画风、光照、构图、适用头部姿态/镜头注视及中性表情项：本色/画风对原素材，其余对本轮呈现目标。特写的构图、头部姿态、注视目标和表情必须各列一项，不合并为“呈现符合”；观察及判定方法见 [呈现验收](presentation.md#呈现验收)。关键纹样、材料及连接在相应分组各列具体项，保持细节输入用途到检查项的对应关系，不能用一个“设计符合”概括全部。图片选用文档、文字底稿与脚本均不能替代回看真实细节图。

默认构图目标由助手统一：头顶主体及重要头饰完整，飞丝触边允许；特写胸部及以上；左侧朝画面左且接近侧面。不以制作模型写入的百分比留白、锁骨硬线、精确角度收紧它。用户明确要求覆盖时在相应framing项写`requirement_origin:"user"`及`user_requirement`实际原话，否则prepare规范化为默认尺度。

每条 `look` 目标增加单一 `aspect`：`color_style`（本色/画风）、`lighting`（光照）、`framing`（构图）、`head_pose`（头态）、`gaze`（视线）、`expression`（表情）。同一视图每种aspect各一条；特写/正面须覆盖六项，背面/侧面至少前三项，其他项按可见内容补充。具体细节仍在目标与观察中展开。用户另指定或合理不可见时写明相应目标及依据，不能省略必查项。各项均须实际复检，不能自动填为通过。

`task_mode:"production"` 用于常规整套制作（完整套省略时也按production检查）；评审既有图片明确写 `"existing_review"`，完整交付清单每套也写相同的 `task_mode`。单张评审默认existing_review，不强制三选一。只生成试跑和未验收既有图片打包使用未验收状态及文件检查，不调用批准门槛，不因跳过三选一而升级图片。

## 看图后填写当前状态

`验收状态.json` 按阶段绑定目标、当前候选、证据和有效依赖；每项实际查看后写原始证据观察、候选观察、结论和证据。不同项可共用同一张适用对照，不必制造无用图片。待核对/失败写 `pending`/`fail`，只有全部通过才能 `approved`。

```json
{
  "schema_version":2,"rules_version":2,
  "brief_file":"制作记录/验收目标.json",
  "stages":{"head":{
    "target_sha256":"本阶段目标绑定哈希",
    "image":"候选/000001_特写.png","sha256":"实际哈希",
    "decision":"unreviewed","dependencies":{},
    "checks":[{
      "id":"本任务身份关系","result":"pending",
      "reference_observation":"实际原始证据观察",
      "candidate_observation":"实际候选观察",
      "comparison_basis":"实际对照的身体/头部关系与可比范围；大致合理即可，必要争议才测量",
      "evidence":[{"file":"制作记录/对照/身份对照.png","sha256":"实际哈希",
                   "candidate_sha256":"当前候选哈希","purpose":"reference_compare","viewed":false}]
    }]
  }}
}
```

复核者明确返回实际模式、`viewed_evidence_ids` 和逐项观察/结论，助手据此生成证据路径、用途、哈希及查看记录，不自动填 `viewed:true`。按 [输入细节逐项对照](visual-verification.md#输入细节逐项对照) 实际打开每组对应部位，再写该项观察与结论；缺对照、未看或看不清的关键细节不能预填通过。特写构图看候选整幅，按 [位置与占比](presentation.md#特写位置与占比) 记录头部主体性、身体占比及是否明显偏下；面部合理偏移可通过，不要求中心测量。有用户指定镜头样例时可补整幅并排，不能仅用重新居中的脸部裁切。合理不可见的事实注明范围与其他视图证据；确定细节错误时撤销该版本及受影响下游的批准。

`viewed:true` 是执行者对实际打开图像的记录，脚本不证明这件事发生过，更不判定观察正确。透明阶段用 `background_policy:{"mode":"transparent","alpha_source":"model或tool_extraction"}`：model表示生成时直接输出Alpha，tool_extraction表示用现行四种方法本地抠像。透明空白样本写 `empty_background_samples:[{"xy":[x,y],"alpha":0,"confirmed_empty":true}]`，背景证据包含实际查看的深浅底PNG，分别标 `background:"dark"` / `"light"`，或一张`backgrounds:["light","dark"]`的alpha_compare拼图。本地抠像保存真实输入、方法/参数和输出哈希旁录，边缘/主体/材料仍须看图。

白底阶段背景检查另写 `empty_background_samples:[{"xy":[x,y],"rgb":[255,255,255],"confirmed_empty":true}]`，RGB填真实源PNG空背景采样，不能采到主体或抄提示词。用户另要求严格纯白时写 `background_policy:{"mode":"exact_white"}`；实际不支持Alpha或本次透明输出不可用的RGB降级阶段可写 `{"mode":"near_white_rgb_fallback","alpha_limitation":"input或output或both","reason":"实际能力限制依据"}` 并在底稿标明近白目标。须视觉接近中性白；不能为让失败通过虚构能力限制。

证据用途按分组记录：身份/设计/呈现为`reference_compare`，原生质量为`native_detail`，缩小表面为`reduced_view`，背景源图为`source_background`，空间关系为`cross_view`。原生/缩小/背景项必须含对应主要证据，也可附原图或其他视图作为`context_reference`，不因附带比较依据而拒收。默认文字呈现的 `reference_compare` 可以是实际查看的候选全图/适用局部与固定文字目标的核对记录，注明文字依据，不伪造图片并排；身份与服饰细节仍须真实图片对照。身份/设计/空间项还写`comparison_basis`说明主体尺度或实际关系依据。这些字段使不适用/缺失的检查可被拦截，不表示脚本能验证判断正确。

## 阶段绑定与三选一

完整套依赖：特写无上游；正面引用合格特写；背面引用合格正面；左侧面引用合格正面及背面。依赖同时绑定上游当前图片和批准所依据的阶段目标/选择版本，不能仅凭同名文件或同一图片哈希沿用已失效目标。

v2的每阶段 `target_sha256` 绑定该阶段目标及它实际使用的来源；`selection_sha256` 绑定该阶段选择记录，不绑定整份四阶段文件。依赖绑定由助手生成，门禁据当前内容重算。后续阶段增加记录不影响已完成上游；目标、图片、来源、证据、选图或有效上游改变，只撤销相应阶段及受影响下游。补机械字段不能自动恢复视觉批准。

首张完整复核通过只批准保底版本，门禁 `--baseline` 验证它可触发固定追加，不代表本阶段已完成。正常制作按 [三选一](quality-and-revision.md#合格视图三选一) 追加两次、排序并核验最终偏好；偏好新增图未通过则回退仍有效的首张。落选追加图允许没有检查表或视觉结论。当前最终状态绑定实际采用的图、有效完整复核及阶段选择，完成阶段门禁后才调用下游；不能先用首张制作下游再随意替换上游。

production完整套保留 `selection_file:"制作记录/三选一记录.json"`，阶段内保存对应 `selection_sha256`，格式见 [三选一记录接口](selection-record.md)。当前PNG与所选候选不同（例如抠像）时，保存连续输入/输出哈希与真实后处理旁录，复检受影响内容。普通处理的逐项证据仍须对应实际当前PNG。仅PNG重编码/透明扩边经脚本重算可见RGBA完整保留、目标和上游未变，再由制作模型看当前全图及深浅底、确认构图和背景通过时，可继承既有质量批准，保存approval_basis与旧复核完整快照。当前文件哈希仍更新；dependency_binding_sha256沿用原人物内容绑定，避免未变内容的下游全体重审。任何可见颜色/Alpha变化、裁切或人物变形都不走此简查。

单张评审/返工用 `scope:"single_stage"`，只记录本次范围和实际基准，不宣称整套通过。既有图片评审 `task_mode:"existing_review"` 不要求缺失的生成历史，也不凭补齐记录表升级合格。

## 调用前和交付前检查

```bash
python "<技能目录>/scripts/review_gate.py" "<验收状态.json>" --root "<项目根目录>" --stage head --baseline
python "<技能目录>/scripts/review_gate.py" "<验收状态.json>" --root "<项目根目录>" --before front
python "<技能目录>/scripts/review_gate.py" "<验收状态.json>" --root "<项目根目录>" --stage head
python "<技能目录>/scripts/review_gate.py" "<验收状态.json>" --root "<项目根目录>"
```

`--baseline`与`--stage`联用，只核查首张批准及其有效目标/证据/依赖，不要求尚未发生的两次追加；`--before`只检查进入该阶段所需的合格依赖，不表示新图已通过；`--stage`核查当前单个阶段的最终状态及选择；不加参数核查完整四张。候选/拒绝、漏项、失败/待核对项、缺观察/未记录查看、图片/来源/证据变更、错误上游版本均须阻断。复制最终图后更新路径但哈希须保持，再核查。

达到上限的 `limit_selection` 单独核查真实调用累计、制作模型选优报告及当前版本；不要求合格首张、固定三张或检查表，也不把原失败改为通过。选中仍有效的合格图时复用原批准；否则`record_integrity_valid/downstream_ready`只表示记录有效且可继续，`recorded_approval_valid:false`、`visual_assessment:selected_without_approval`表明包含未验收选图。门禁退出成功不等于图片合格。修改目标、图片或上游仍使受影响记录失效。

报告分别列文件完整性、记录/版本一致性、记录中的视觉决定，不合并成“图片通过”。输出明确 `scope:review_records_and_versions` 和 `model_visual_checks:false`。脚本只能查记录完整性和版本，不能识别变脸、改款、空间矛盾或脏点。不能把它的批准记录核验当成独立视觉认证；真实视觉判断仍由执行者承担。

脚本需要Pillow完整解码候选及读取背景采样像素，按透明/严格纯白/能力降级近白策略核查实际Alpha或RGB；缺少Pillow时明确报错。空白坐标的选择是否正确、背景整体是否均匀仍须看图判断。
